## Where things stood

0.1.0, private, not on WordPress.org. Settings → Social Login was a classic
Settings API screen. Open issues: #1 (Settings link), #2 (React screen), #4
(decision log). No paid add-on was planned.

## What was done

- 0.2.0: Settings → Social Login is a React app (`admin/src`, built into
  `admin/build`) with the shell, colours and dark mode of NHR Issue Reporter.
  It reads and saves through `GET`/`POST nhrrob-social-login/v1/settings`
  (`manage_options`); the secret never comes back, only whether one is set.
- A Settings link on the Plugins screen (#1), this decision log (#4).
- Hooks for an add-on: `nhrrob_social_login_signed_in`, `nhrrob_social_login_enqueue`
  and the `nhrrobSocialLogin.app` JS filter.
- Checked on the dev site in Playwright: the screen in light and dark at
  1280px and 390px (no horizontal scroll, no console errors), saving, the
  button at the top of the login form, and a whole sign-in from a comment
  form against a stand-in for Google's token endpoint: back on the post,
  logged in as a new Subscriber, the hook fired with `created: true`.

## 0.3.0: the free roadmap (#11 to #22)

Robin asked to complete every open issue. One branch, `release-0.3.0`, one pull request.

- Providers: `includes/Providers/` with a base class and seven providers; `Jwt` for the shared token code; `Callback` for the new redirect URIs. Google's URI and meta key are unchanged.
- Profile linking, avatars, roles, redirects, block and shortcode, One Tap, allowed domains, WooCommerce, the owner's email, sign-in links by email, the verified mark: one class each, listed in `FEATURES`.
- The app: Providers (one card each), Accounts and Extras. REST takes `{ providers, settings }`.
- Found while checking: counting linked users with one `EXISTS` clause per provider joined usermeta seven times and hung; it is one `IN` on the key now. Block themes print the comment author with the Comment Author Name block, so the verified mark hooks that block too.
- Checked on the dev site (login page moved to `/access` by NHR Secure) with Playwright against stand-ins for the providers (a temporary mu-plugin for their servers, routes for their pages), 44 checks: Google from a comment form, Apple's cross-site form_post, GitHub on the callback path, profile link and unlink, sign-in links (once only), One Tap (forged signature and another browser's nonce refused), shortcode and block, the verified mark and avatar, the REST route never returning a secret and refusing editor and administrator roles, the three screens in light and dark at 1280px and 390px, no console errors.
- WooCommerce was installed on the dev site for the check (buttons in My account's login and register forms, back to the same page, Customer role for new accounts), then removed with its pages. Checkout was not opened, since it needs a cart.
- Not checked against the real providers: no client credentials on the dev site.
