# Decisions

Why NHR Social Login is the way it is, and whether each choice can be
undone. One row per decision, newest last. A pull request that makes a
decision adds its row; reversing one strikes the old row and adds a new one.
The reasons behind the first version are in [PRD.md](../.ai/PRD.md), "Decisions and why".

| Date | Decision | Why | Can it be undone? | Who |
| --- | --- | --- | --- | --- |
| 2026-10-16 | Account creation is the plugin's own setting, never "Anyone can register"; new accounts are Subscribers | Keeps WordPress's registration form closed to bots; a verified Google address is far harder to fake | Yes | Robin |
| 2026-10-16 | Accounts are linked by Google's `sub`, never relinked to another `sub` | An email address can change hands; the `sub` never does | Hard: existing links would need moving | Robin |
| 2026-10-16 | The ID token's signature is not checked; issuer, audience, expiry and nonce are | It comes straight from Google's token endpoint over TLS, which OpenID Connect allows | Yes | Robin |
| 2026-11-24 | Settings → Social Login is a React app with the shell of the other nhrrob plugins (Issue Reporter's "Aurora"), light and dark, closing #2 | Robin's rule for every plugin's admin screen; Pro adds its screens to the same app | Yes | Robin's rule |
| 2026-11-24 | The free plugin fires `nhrrob_social_login_signed_in( $user, $context )` and `nhrrob_social_login_enqueue`, and the app takes screens through the `nhrrobSocialLogin.app` JS filter | What an add-on needs to count sign-ins and show its screens, without reaching into the plugin | Hard once an add-on uses them: they stay as they are | Claude |
| 2026-11-24 | The login button is moved to the top of the form by `assets/login.js`, enqueued, instead of an inline script | WordPress.org's Plugin Check flags scripts printed inline | Yes | Claude |
| 2026-11-24 | The repo goes public and the plugin to WordPress.org; business documents live only in the private Pro repo | Robin's rule for every plugin: the free repo is public | Making it private again does not unpublish what was seen | Robin |
| 2026-11-24 | Releases by hand (a GitHub release makes the tag), deployed to WordPress.org by the tag; `release.yml` that tagged on a version change is removed | The same as Secure and Post Insights; a tag is now also a WordPress.org release | Yes | Robin's rule |
| 2026-11-24 | `package.json` and `admin/src` ship in the zip | WordPress.org asks for the source of built code | Yes | Claude |
| 2026-11-24 | A pushed tag `v<version>` is the whole release: the tag push deploys to WordPress.org and makes the GitHub release, which is no longer made by hand | Robin: fewer manual steps, the same in every plugin | Yes | Robin |
| 2026-11-24 | A provider is a class in `includes/Providers/` (Google, Microsoft, Apple, GitHub, Facebook, X, LinkedIn); links are `nhrrob_social_login_<provider>_sub`, Google's key unchanged; closes #11 | `Login` stays the flow, another provider is one class; existing Google links keep working | Hard once users link: the keys stay | Claude |
| 2026-11-24 | Google keeps `admin-post.php?action=nhrrob_social_login` as its redirect URI; the others answer at `/nhrrob-social-login/callback/<provider>/`, a rewrite rule | Existing Google clients keep working; Microsoft refuses redirect URIs with a query string for personal accounts | Hard once owners register the URIs | Claude |
| 2026-11-24 | Microsoft work and school addresses are taken only with the `xms_edov` claim; personal accounts' addresses are taken as verified | An organisation can type anyone's address into its tenant (the nOAuth problem); a verified email is this plugin's rule | Yes | Claude |
| 2026-11-24 | Apple's form_post is turned into a 303 GET to the same address, keeping the state cookie SameSite=Lax | A cross-site POST drops a Lax cookie; SameSite=None would weaken the cookie for every provider | Yes | Claude |
| 2026-11-24 | One Tap's ID token has its RS256 signature checked with Google's published keys (cached), and its nonce against a cookie the page's script sets; closes #17 | That token passes through the browser, unlike the code flow's; a nonce in a cookie keeps cached pages working | Yes | Claude |
| 2026-11-24 | New accounts never get a role that can manage options or users, and a role that can write posts only after the owner ticks a warning; closes #14 | A sign-in at a provider is open to anyone; administrator by mistake would be a takeover | Yes | Claude |
| 2026-11-24 | Sign-in links by email are a screen on the login page (`wp-login.php?action=nhrrob_social_login_email`); the link opens a page with a button, tied to that browser by a cookie; closes #21 | The login and comment forms are forms already, so a second form cannot sit inside them; mail scanners that open links would use up a one-time link | Yes | Claude |
| 2026-11-24 | Whether a user has a Gravatar is asked once, at sign-in, and kept in user meta; closes #13 | No request on page views; Gravatar's own fallback cannot take Google's picture addresses, which have no file extension | Yes | Claude |
| 2026-11-24 | Unlinking the last provider is refused while the account has only the random password the plugin gave it (`nhrrob_social_login_no_password`, cleared when a password is set); closes #12 | Keeps a way in, as the issue asks | Yes | Claude |
| 2026-11-24 | The settings app has three screens: Providers (the `setup` id, so the add-on's links keep working), Accounts and Extras | Twelve features on one screen would be a wall; no new mockups were drawn on the canvas first, the screens reuse the existing shell, cards and steps | Yes | Claude, for Robin to review |
| 2026-11-24 | Add-ons get two filters, `nhrrob_social_login_button_extra` (markup after the button, through a fixed `wp_kses()` list) and `nhrrob_social_login_start_data` (data kept through the sign-in, back as `data` in the context), instead of a button an add-on draws itself | An opt-in checkbox next to the button has to reach the sign-in it starts; a narrow allow-list keeps add-on markup from printing anything else | Yes, but they stay once an add-on uses them | Claude |
| 2026-11-25 | The admin app follows the NHR UI contract: the root also carries `nhr-app`; its brand, surface, text, border, radius and font tokens read a shared `--nhr-*` variable first with its own value as the fallback; `window.nhrUi.theme` (`light`, `dark`, `system`) fixes the theme and hides the toggle; the `nhr_admin_parent_menu` filter can move the screen under another menu | One look and one menu across NHR plugins when a site asks for it. Nothing defines `--nhr-*` or `nhrUi` on its own, so the screen looks and sits as before | Yes. Drop the fallbacks, the class and the filter | Robin |
